Workshop

From Click to Database

Build a small shop end to end and see how every layer connects: React in the browser, an Express API, and a Postgres database on Neon.

The big picture

Today we build every arrow in that picture, one small step at a time.

What you will build: Mini Shop

  • A product page with category filters, built from real data
  • A small API with a health check, CORS and a database
  • An Add product form that is protected by validation
  • A shopping cart that shares its state across the whole app

The styling is already done, so you only write TypeScript and JSX.

1. The delete endpoint

2. Meet Postman

Postman is a tool for sending requests to an API and reading the answers. It is not a browser, so there is no CORS and no form, which makes it perfect for testing a backend on its own.

  1. Open Postman and create a new HTTP request.
  2. Choose GET, enter http://localhost:3001/api/products and click Send. You see the JSON array.
  3. Create a POST to the same URL. Open Body, choose raw and JSON, paste the faulty product below, and send it.
  4. Read the answer: 400 and the message. The validation works even without our form.
  5. Change the category to Home and send again: 201 Created, and the response has the new id.
  6. Create a DELETE to http://localhost:3001/api/products/<that id> and send it: 204 No Content. Send it again: 404.
Short on time?

Import the ready-made collection: in Postman choose Import and pick postman/mini-shop.postman_collection.json. It has Health, List, Create (clean), Create (faulty) and Delete.

Checkpoint

In Postman: GET returns the list, the faulty POST returns 400, a clean POST returns 201, DELETE returns 204 then 404. Back in the browser, reload: the deleted product is gone.

3. A word about env files

  • server/.env holds values that change between machines or are secret: the port, the allowed website, the database password.
  • It is in .gitignore, so it is never committed. .env.example is committed instead, with empty values, to show what is needed.
  • In production (Render, Vercel) the same names are set in the hosting dashboard, not in a file.
  • The server reads them once, in config.ts. The rest of the code imports config and never touches process.env.
SayAsk: what would happen if we committed the .env file? Anyone who sees the repo could use your database. Rotating the password would fix it, but only if you notice.

Step 8

The cart and global state

Add the cart. This is the one place where many components need the same data, so we meet a store.

Time 3:00 to 3:15 (15 min)Branch at the end step-8-cart-zustand (the same as final, apart from the deploy files)Topics global state, zustand
Files that change in this step (4)
  • edited client/src/App.tsx
  • new client/src/components/CartDrawer.tsx
  • edited client/src/components/ProductCard.tsx
  • new client/src/store/cartStore.ts

1. Why a store?

Three different components care about the cart: the Add to cart button on every card, the badge in the header, and the drawer. They sit in different parts of the tree.

  • With local state we would have to pass the cart down through props, through components that do not care about it.
  • A store lives outside the component tree. Any component can read it or change it directly.
  • zustand is a tiny library for this: one function, no providers.

2. The store (type this)

  • create builds the store. The object holds the data (items) and the actions that change it.
  • set((state) => ...) builds the next state from the previous one. It never mutates the old array.
  • useCartStore((state) => state.add) reads only the piece you need, so a component re-renders only when that piece changes.

3. Connect the UI

The drawer is plumbing, so paste it. The interesting change is that nothing is passed through props.

Checkpoint

Add to cart on a few products: the badge in the header goes up. Switch to another category and add more, and the badge keeps counting, because the cart is not tied to the list. Open the cart, change a quantity (the total updates), and remove an item.

SayThis is global state. Compare: the filter (step 1) is local state with one owner. The cart is global state with many readers. Use local state first and reach for a store only when sharing starts to hurt.

Bonus

Keys and the React Profiler

A small lab about why the key prop matters and how to measure re-renders. Do it if there is time, or at home.

Branch bonus (built on top of final)Time about 15 min

1. Get the lab

Open http://localhost:5173/?lab=keys.

2. Part A: keys

  1. Type a different note into each row.
  2. Click Remove first. With key=index the notes stay in their positions, so they end up under the wrong items.
  3. Click the toggle to switch to key=id, click Reset, and repeat. The notes now follow their items.
SayReact uses the key to decide which element belongs to which item. With an index, the item at position 0 is always 'the same one', even after you delete it.

3. Part B: Profiler and React.memo

  1. Click Re-render parent a few times and read the Profiler line. With memo on ProductCard the 100 cards barely re-render (about 0 to 1 ms).
  2. In ProductCard.tsx change the last line to export default ProductCard;, save, and click again. It takes about 10 ms.
  3. Put memo back.
Measure before you optimise

memo skips a component when its props did not change. Most components do not need it. Use the Profiler to find the ones that do.

1. Push your code to GitHub

2. API on Render

  1. Render dashboard > New > Blueprint, pick your repo and the final branch. Render reads render.yaml.
  2. Set DATABASE_URL to your Neon string. Leave CLIENT_ORIGIN for now.
  3. Open https://<your-service>.onrender.com/api/health. You should see {"status":"ok"}. This is the health endpoint from step 2, and Render calls it to know your app is alive.
Why is tsx a normal dependency?

Render installs only production dependencies. The server runs TypeScript through tsx, so on the final branch it is listed as a normal dependency.

3. The same database

You already seeded your Neon database in step 3. Render connects to that same database through DATABASE_URL, so there is nothing more to seed.

4. Client on Vercel

  1. Vercel > Add New > Project, pick the repo.
  2. Set Root Directory to client and turn on Include source files outside of the Root Directory (the app lives in an npm workspace). Preset: Vite.
  3. Add the environment variable VITE_API_URL = https://<your-service>.onrender.com/api.
  4. Deploy and copy your Vercel URL.

5. Whitelist your site

The CORS lesson again, for real: in Render set CLIENT_ORIGIN to your Vercel URL, with no trailing slash. Render redeploys by itself.

Plan for about 150 minutes of content in 210. A group new to React takes 1.5 to 2 times as long at each step. The final steps are where you will feel it.

Before the day

  • Run the whole workshop yourself once from a clean clone, ideally on a different laptop and a fresh Neon project.
  • Send the prerequisites a week ahead and ask everyone for a screenshot of npm run check.
  • Open on the projector: the finished app on final, the Neon dashboard, Postman, and the demo video.
  • Neon is mandatory. Make sure everyone can sign up. A student whose Neon fails pairs with a neighbour.
  • Check the venue wifi and bring a phone hotspot. npm install is the biggest risk.
  • If you will run the quiz, test it with real phones on the venue wifi.

Running the room

  • Type the lesson, paste the plumbing. The guide marks each file as type-along or paste.
  • One checkpoint per step. Do not move on until most people see it.
  • Pair beginners with stronger students from step 3 on.
  • Do not debug one laptop for more than two minutes. Give them the catch-up command and come back later.
  • Never lose the thread. Re-draw the big picture on the board at the start of steps 2, 3 and 4.

If you are running late: cut order

  1. Step 8: demo it from the branch instead of typing it (the cart is a good demo).
  2. Shorten the quiz to 6 questions.
  3. Step 7: skip the delete endpoint and keep only Postman: GET and POST.
  4. Step 4: paste the hook instead of typing it.
  5. Never cut: the big picture, step 3 (the database), the faulty product demo, and the catch-up commands.

Running the quiz

A live Kahoot-style quiz: 12 questions, 20 seconds each, faster correct answers score more. The top three win 3, 2 and 1 mentoring sessions.

  • Open the host URL printed in the terminal on the projector browser and press F11. Players scan the QR code on that screen.
  • Space continues, M mutes. Click a name in the lobby to remove a player.
  • Rehearse alone with fake players: PIN=<pin> npm run bots -- 12, and join once from your own phone.
  • Edit questions, timings and prizes in quiz/questions.mjs.
Test the wifi before the day

Many venue networks block phones from reaching your laptop (client isolation). Test with a few phones at the venue. Fallback: run cloudflared tunnel --url http://localhost:3000 and start the quiz with PUBLIC_URL=<tunnel address> npm start, so students can use mobile data. Details in quiz/README.md.

Questions you will get

QuestionShort answer
Why TypeScript and not JavaScript?Types catch mistakes while you type. The code is the same, so beginners can ignore the annotations at first.
Why not Next.js?One new tool at a time. Next.js is the natural next step and uses the same React ideas.
Why fetch and not axios?Fetch is built in, so there is one less package to learn. Axios works just as well.
Why zustand and not Redux or Context?It is the smallest way to show the idea of a store. Redux and Context solve the same problem with more setup.
Is the Neon free tier enough?Yes, for a workshop and small projects. It scales to zero when idle.
How do I add login?A users table, hashed passwords, and a session or JWT. A great follow-up project.
Can AI write this for me?It can draft it. You still need to read, run and understand every line, or you cannot debug it.
